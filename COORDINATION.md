# Coordenação das três execuções (V76)

Três automações horárias, escalonadas no horário Europe/Lisbon: investigação :10, desenvolvimento :30, auditoria :50. Os horários são oportunidades de execução, não uma garantia de início/fim. Se houver sobreposição, só quem adquirir o bloqueio remoto trabalha; as restantes saltam o ciclo. Não esperar indefinidamente nem forçar o desbloqueio. Os 10 papéis e o RH freelance do AGENTS.md são preservados.

## Protocolo obrigatório
- Cada papel usa um clone/pasta exclusiva (research-team, development-team, audit-team, dentro de BarretoLabs/ViseuAgenda no PC autorizado), ou ambiente cloud isolado. Nunca partilhar a working tree. Confirmar origin e sincronizar viseu-pages; ler AGENTS.md, ROADMAP.md, BACKLOG.md, ARCHITECTURE.md, DESIGN_SYSTEM.md, DATA_SOURCES.md, KNOWN_ISSUES.md, QUALITY_GATES.md, CHANGELOG.md, SPECIALISTS.md e este documento. Usar Python 3 e Git, sem novas dependências.
- Antes de investigação, testes ou edições, executar `python scripts/pipeline_lock.py acquire <research|development|audit>` no clone sincronizado. Guardar o token devolvido apenas no contexto local. Exit 2 = ocupado/conflito; exit 1 = erro: parar sem alterações, não publicar. Verificar `status` se necessário. Não iniciar trabalho se o lock remoto não estiver confirmado. Não usar apenas ficheiro local ou relógio como lock.
- `coord/pipeline` é uma branch de coordenação append-only (não a publicação): contém state.json e três handoffs JSON. O lock usa commits filhos e push fast-forward, sem force. Duas tentativas sobre o mesmo pai só admitem uma atualização. Em caso de erro ambíguo, verificar remoto e falhar de forma conservadora. Apenas o dono/token pode libertar o lock pelo script. Não partilhar token fora da coordenação. Não alterar manualmente essa branch.
- `python scripts/pipeline_lock.py status` mostra os três handoffs mais recentes. Ler antes de escolher trabalho; a informação é partilhada pelo Git, não por leitura presumida de outros chats. A conclusão de uma execução não dispara automaticamente outra.
- Em finally, após terminar toda a atividade (incluindo subprocessos), guardar handoff JSON sanitizado em ficheiro temporário exclusivo e executar `python scripts/pipeline_lock.py release <role> <token> --handoff <path>`. Se não houve progresso, libertar sem --handoff e preservar a última entrega. Confirmar estado idle remoto. Não libertar enquanto houver trabalho em curso. Se falha/interrupção deixar lock ativo, não expirar nem roubar automaticamente; reportar bloqueio, exigir confirmação de que o dono e processos terminaram antes de recuperação manual autorizada. Um lock preso é preferível a alterações concorrentes.
- Handoffs e commits são públicos: nunca incluir segredos, dados pessoais, ficheiros brutos de licença desconhecida, dados privados ou credenciais. Evidências grandes ficam no diretório autorizado, com caminho relativo, contagem, hash, fonte e instruções reproduzíveis. Usar novos resultados com validade confirmada; referências a ficheiros locais indisponíveis não são prova de acesso.

## Responsabilidades e passagem
**Research:** Product Manager, Data Engineer, RH tecnológico e especialistas conforme necessidade. Investiga fontes oficiais/abertas, qualidade, licenças, ferramentas e hipóteses novas; entrega dados validados e instruções reproduzíveis. Não altera site, candidato ou publicação. Handoff: id/data, base SHA, problema, fonte/licença, resultados/contagens, testes, artefactos autorizados ou instruções, bloqueios, prioridade, critérios de aceitação. Atualizações de backlog/fontes/especialistas propostas ao desenvolvimento.

**Development:** Tech Lead, UI/UX, Frontend, Backend, com apoio de Data Engineer/RH. Lê handoffs de research e audit. Resolve regressões primeiro, depois maior impacto. Se existir candidato pendente de revisão, não o sobrescrever: aguardar auditoria ou preparar trabalho local sem publicar outro candidato. Implementar em branch única candidate/<data-utc>-<slug> a partir de SHA atual de viseu-pages. Atualizar documentação pertinente, testar conforme QUALITY_GATES.md, enviar branch sem force, confirmar SHA remoto. Nunca alterar viseu-pages. Handoff: id, research id (se aplicável), base SHA, branch, candidate SHA, ficheiros, testes, resultados, riscos, evidências e status ready_for_review. Se gates falham, status blocked, não pedir aprovação. Para rejeição, criar novo candidato a partir da base atual, referenciar revisão anterior.

**Audit:** QA, Security & Compliance, DevOps; revisão independente da execução de desenvolvimento. Ler candidato e handoff; verificar branch, base e SHA exatos, diff, licenças e segurança, testar fluxos críticos desktop/mobile, sem depender de alegações de testes de outra equipa. Só aprovar se todos os gates aplicáveis passam. Único papel autorizado a publicar: verificar que viseu-pages ainda é exatamente base SHA, candidato é descendente dessa base, push fast-forward do SHA aprovado para viseu-pages (sem force); revalidar versão/conteúdo/recursos e smoke test público. Se base mudou, rejeitar como stale, pedir rebase e novos testes, nunca sobrescrever. Se Pages ainda anterior, registar deploy pending, verificar na próxima execução. Se regressão comprovada, reverter apenas o commit próprio com revisão e reteste. Handoff: candidate SHA, verdict approved/rejected/stale/deploy_pending/published, evidência, testes, falhas, publicação SHA/URL ou pendência. Se não há candidato, auditar site público, registar regressões acionáveis, não inventar entregas.

## Decisões e métricas
Usar máximo raciocínio disponibilizado em cada execução, sem fingir seletor Extra High ou agentes paralelos. Não confundir investigação com entrega; só comunicar avanço material, incidente, rejeição acionável ou bloqueio que exige atenção. O desenvolvimento incorpora documentação de pesquisa/auditoria e histórico de especialistas. Preservar todas as restrições de AGENTS.md e autorização do utilizador. A alteração manual autorizada pelo utilizador deve verificar lock idle e SHA antes de publicar; se publicação mudou, candidato anterior fica stale.
